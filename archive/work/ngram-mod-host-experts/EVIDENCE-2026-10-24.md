# EVIDENCE 2026-10-24 — the `ngram-mod` draft width vs the MoE arena's 16-token decode band

**Status:** root cause identified, reproduced and **fixed in r123 (block 09, TODO #59 closed)**.  This
directory is the campaign's record; nothing here is part of the delivery.  The rule is
`GREEDY-PURITY.md` §50, the block reference is `patches/README.md` (block 09), and the release note is
`WORKLOG.md` 261024.002.

## 1. The mechanism (one paragraph)

`ngram-mod` drafts **48-64 tokens** by default (`common_params_speculative_ngram_mod`: `n_match 24`,
`n_max 64`, `n_min 48`; issue #214 uses `--spec-ngram-mod-n-max 256`).  A speculative verify batch is
`n_draft + 1` rows, so on host-resident MoE experts it is **wider than the MoE expert cache's decode
band** (`MOE_EXPERT_CACHE_MAX_TOK`, 16 on RDNA4 — `moe_cache_max_tok_dev()`).  The cache serves the
band from the arena in VRAM; **above the band the MoE op leaves the arena entirely**
(`moe_cache_update_host()` returns `false` for `n_tok > band`, the `reaches` counter collapses) and the
routed experts are streamed from the pinned `ROCm_Host` master over the per-op upload path instead.
On this box (PCIe 5.0 **x4** per card) that is a hard discontinuity, not a slope: the in-band
verify is served from VRAM, the out-of-band one moves a large slice of the host expert set every
step.  MTP alone never hits it because `--spec-draft-n-max` is already clamped to 15
(`common_init_from_params`), i.e. a verify of at most 16 rows — exactly the band.  `ngram-mod` has no
such clamp, so the README's `draft-mtp-adaptive,ngram-mod` recommendation puts *every ngram step*
outside the band on a host-expert config.

## 2. The cliff is exactly at width 17 (band + 1)

Host-expert cell: **2x R9700 (`HIP_VISIBLE_DEVICES=0,1`), `-sm tensor -ncmoe 36`,
Flash-Next `IQ4_NL` + `mtp-...-shared-Q8_0`, `-c 16384 -b 2048 -ub 512 -t 8`,
`prompts/recall.txt`, `-n 2000 --temp 0 --seed 42 --reasoning off`**, expert cache auto
(arena 32.9 GiB, 57 % of the host set resident).  Arms: `draft-mtp,ngram-mod --spec-draft-n-max 3
--spec-ngram-mod-n-match 45 --spec-ngram-mod-n-min 0`, sweeping `--spec-ngram-mod-n-max K`.

| `--spec-ngram-mod-n-max` K | widest verify | gen t/s | mean acc len | arena MiB | arena hit |
|---:|---:|---:|---:|---:|---:|
| 4 | 5 | 96.7 | 4.87 | 32937.9 | 0.9774 |
| 8 | 9 | 120.3 | 8.02 | 32318.3 | 0.9774 |
| 12 | 13 | 154.8 | 10.80 | 32937.9 | 0.9774 |
| 15 | **16 (in band)** | **159.2** | 12.43 | 32318.3 | 0.9776 |
| 16 | **17** | **55.0** (repeat 55.2) | 13.08 | 32937.9 | 0.8984 |
| 20 | 21 | 58.1 | 15.06 | 32937.9 | 0.9010 |
| 24 | 25 | 58.3 | 16.03 | 32937.9 | 0.9010 |
| 32 | 33 | 48.1 | 19.88 | 32937.9 | 0.8934 |
| default (64/48) | 65 | 74.1 | 27.61 | **27814.2** | 0.8926 |

`K=16 -> 17 rows` is a **2.9x** step (159.2 -> 55.0 t/s) for one extra row, and the arena hit rate
drops 97.8 % -> 89.8 % while the counted `reaches` fall 1086540 -> 129660: the wide steps no longer
reach the cache at all.  Per step: 13.08 accepted tokens / 55.0 t/s = 238 ms vs 12.43 / 159.2 = 78 ms.
The 32-token op-offload staging-ring gate does **not** rescue it (K=32 is worse), so the cost is
traffic, not the synchronous-vs-async upload.

The uncapped arms also lose ~5 GiB of arena: `n_rs_batch = common_speculative_n_max() + 1` (= 65 with
`n_max 64`) is the graph width the slab's *narrow floor* is measured at (`graph_reserve(n_rs_batch, ...)`
in `llama-context.cpp`), so a deep ngram draft reserves a wider verify compute layout and the arena is
sized against a smaller free region.  Wide drafts therefore hurt twice: they leave the band *and* they
shrink the arena that would serve it.  (At `K=15` the arena is 32318-32938 MiB.)

## 3. The documented README combo, with and without the cap

`--spec-type draft-mtp-adaptive,ngram-mod --spec-draft-n-max 9 --spec-ngram-mod-n-match 45`,
same cell:

| arm | gen t/s | mean acc len |
|---|---:|---:|
| ngram defaults (64/48) — the README recommendation | 73.9 | 35.50 |
| ngram capped to the band (`--spec-ngram-mod-n-max 15 --spec-ngram-mod-n-min 0`) | **168.3** | 14.20 |

**+128 % (2.3x)**.  This is the TODO #59 symptom: the combo is not "roughly half" of plain
`draft-mtp-adaptive` because of anything MTP does — it is the ngram draft width falling off the band.

## 4. Controls (why this is the host-expert serve path and nothing else)

Same model, `prompts/recall.txt`, `-n 2000`:

| arm | config | gen t/s |
|---|---|---:|
| plain decode (`--spec-type none`) | 2 GPU, `-ncmoe 36` | 37.5 |
| `draft-mtp` n3 | 2 GPU, `-ncmoe 36` | 101.4 |
| `draft-mtp` n3 + ngram (in band, K=3) | 2 GPU, `-ncmoe 36` | 112.0 |
| `draft-mtp` n3 + ngram default (65 rows) | 2 GPU, `-ncmoe 36` | 74.1 |
| `draft-mtp` n3 | **3 GPU, `-ncmoe 0`** (device-resident) | 144.7 |
| `draft-mtp` n3 + ngram default (65 rows) | 3 GPU, `-ncmoe 0` | **378.7** |
| `draft-mtp` n3 + ngram K=15 (in band) | 3 GPU, `-ncmoe 0` | 244.6 |
| `draft-mtp` n3 | 2 GPU, `-ncmoe 36`, **`MOE_EXPERT_CACHE_MIB=0`** (CPU experts) | 38.5 |
| + ngram default (65 rows) | CPU experts | **67.6** |
| + ngram K=15 | CPU experts | 52.2 |

Three conclusions:

1. **Device-resident: wide drafts are a big win** (144.7 -> 378.7, +162 %) — the README's claim, and
   the reason a *global* ngram cap would be wrong (the in-band cap costs 35 % there: 378.7 -> 244.6).
2. **CPU-compute experts: wide drafts also win** (38.5 -> 67.6) — the weights are local, so extra rows
   only cost compute and the wide batch amortises the per-token overhead.  This is the upstream shape
   and the explanation for issue #214: that report is a 12 GB card / 24-of-40 host layers box where
   upstream (and r120 on that box) computes the host experts on the **CPU**, so the wide ngram verify
   is cheap there and the combo is the 3.4x rewrite win they measured.  There is no cliff to see.
3. **GPU-served host experts (the delivery's arena / op-offload path): wide drafts are a loss**, and the
   loss is a cliff at the band, exactly like the measurement in §2.

So the condition is precise: *host experts served by the GPU through the expert arena*, not
"`-ncmoe` is set".

## 5. The fix (shipped in r123)

Cap the effective draft length of the **draftless ngram speculators** (`ngram_mod.n_max`,
`ngram-simple`/`ngram-map-k`/`ngram-map-k4v` `size_m`) to `band - 1` when the target's expert cache
is **active** (the arena is what makes the wide verify expensive), i.e.:

* new query `moe_cache_band` following the existing `ggml_backend_dev_moe_cache_stats` shape
  (`ggml-backend.h` iface -> CUDA `g_enabled ? moe_cache_max_tok_dev(dev) : 0`), exposed as
  `llama_model_moe_cache_band()` next to `llama_moe_cache_stats()`;
* in `common_init_from_params`, after the model is loaded and after the cache preflight (both the load-time
  and the `common` pass have decided), and **before** `llama_init_from_model()`: clamp `n_max` to `band - 1`,
  lower `n_min` to `min(n_min, n_max)` (the default `n_min 48` would otherwise silently disable ngram
  drafting under the cap) and refresh `cparams.n_rs_batch` (the context params are built before the model
  loads, so `n_rs_batch` -- and with it the slab's narrow verify floor and the GDN rollback bound -- would
  otherwise keep the uncapped width);
* one WRN at `-lv 2` explaining the clamp, and a kill switch
  (`LLAMA_SPEC_NGRAM_MOD_BAND_CLAMP=0`) in the same style as `LLAMA_SPEC_DRAFT_N_MAX_CLAMP`.

Measured after the fix (same cell): the README combo **166.1-168.6 t/s** (four runs), `draft-mtp,ngram-mod`
160.2 t/s, `LLAMA_SPEC_NGRAM_MOD_BAND_CLAMP=0` **74.7 t/s** (the bug, exactly), device-resident 380.2 t/s and
CPU-expert 68.1 t/s both **without** a clamp line (their band is 0).  Text purity with
`ROCBLAS_USE_HIPBLASLT=0`: `plain` / `draft-mtp n3` / ngram hand-capped / ngram auto-clamped all hash
`9d914f47aebb` (1793 chars), identical to the pre-amend build.

Alternatives considered and rejected:

* **Document "use `--spec-ngram-mod-n-max 15`" only.**  Works, but the default is the harmful one and
  the cap interacts with `n_min` (a naked `n_max 15` silently disables ngram-mod on the default
  `n_min 48`), which is a trap.  Do this *as well* if the auto-clamp is declined.
* **A global cap at 15.**  Costs 35 % on device-resident configs, where the wide draft is the product.
* **Widen the band.**  `moe_cache_max_tok_dev()` cannot go above `MMVQ_MOE_MAX_BATCH_SIZE` (16 on
  RDNA4), and it would not help anyway: a 17-65 row verify routes ~a quarter to all of a table's 512
  experts, and this cell's arena holds only 57 % of the host set, so the misses still stream.
* **Serve the wide band from the arena.**  Same arithmetic: with 57 % residency the routed set cannot
  be served from VRAM; would only pay on fully-resident (identity) tables.

## 6. Reproduction

`run-arm.sh` in this directory (one arm per log file; `logs/`).  Example:

```bash
N=2000 bash wip/ngram-mod-host-experts/run-arm.sh sweep-k15 draft-mtp,ngram-mod \
  --spec-draft-n-max 3 --spec-ngram-mod-n-match 45 \
  --spec-ngram-mod-n-min 0 --spec-ngram-mod-n-max 15
```

Env: `GPUS` (default `0,1`), `NCMOE` (default `36`), `N`, `CTX`, `PROMPT`, `LV` (default 3 — the
`draft acceptance`/`MoE arena` lines are INFO).
